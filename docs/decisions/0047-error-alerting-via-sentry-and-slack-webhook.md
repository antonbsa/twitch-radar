# 0047 - Error Alerting Via The Sentry SDK And A Direct Slack Webhook

## Status

Accepted

## Context

[ADR 0040](0040-structured-leveled-logging-convention.md) made failures in `apps/api/src` structured and queryable in Workers Logs, but nothing pushes. An error is only discovered when someone decides to go look. That gap produced a concrete incident: from 2026-09-02, preview's minutely EventSub creation cron logged `EventSub subscription create failed` (HTTP 400) roughly every minute for over a week, and it was found by chance while browsing the Cloudflare dashboard for an unrelated reason. [Issue #73](https://github.com/antonbsa/twitch-radar/issues/73) covers the underlying defect — nothing retires a permanently-failing `pending` row. This ADR covers the other half: there was no signal.

A survey of Cloudflare-native alerting found nothing usable on this project's plan, and mostly nothing usable at all:

- **Cloudflare Notifications** has no Workers entry in its [available-notifications catalog](https://developers.cloudflare.com/notifications/notification-available/) on any plan — no notification type exists for a Worker runtime error, an uncaught script exception, or a failed cron trigger.
- **OpenTelemetry export** (`observability.traces`/`logs.destinations` in `wrangler.jsonc`, which would push logs and traces to Sentry/Honeycomb/Grafana without any SDK) is **Workers Paid only**, and its beta pricing ends 2026-10-01.
- **Tail Workers** and **Logpush** are Paid.
- **Cloudflare Email Service** (the `send_email` Workers binding) is Workers Paid _and_ requires a sender domain onboarded to Email Service. This project serves both API and web from a `*.workers.dev` origin with no custom domain ([ADR 0037](0037-single-public-url-same-origin-deployment.md)), so it fails on two independent grounds.
- The only free email the account emits is usage-limit alerts (e.g. D1's free-tier daily query cap) — a different failure class than an application error.

That leaves exactly one shape of solution on the Workers Free plan: the alert originates **inside the Worker invocation**, over `fetch()`.

Sending through the developer's own SMTP account was considered and rejected. It is technically possible — [`worker-mailer`](https://github.com/zou-yu/worker-mailer) implements SMTP over `cloudflare:sockets`' `connect()` on ports 587/465 with TLS or STARTTLS, and works on the Free plan (only port 25 is blocked; the widely repeated claim that "V8 isolates have no TCP sockets so SMTP is impossible in Workers" is outdated). But a TCP+TLS handshake plus a multi-step SMTP dialogue inside a scheduled invocation costs several round trips against the CPU and wall-clock budget and adds failure modes, to deliver the same payload a single HTTP POST delivers. The SMTP account is better reserved for a future need to send real user-facing mail.

## Decision

- **Error reporting uses [`@sentry/cloudflare`](https://docs.sentry.io/platforms/javascript/guides/cloudflare/)**, the in-Worker SDK, not the platform's OpenTelemetry export. The SDK reports over `fetch()` and depends on no paid platform feature, so it works on the Workers Free plan. It requires `compatibility_flags: ["nodejs_compat"]` in `apps/api/wrangler.jsonc` (for `AsyncLocalStorage`) and a `compatibility_date` of `2024-09-23` or later — the current `2026-06-22` already satisfies the latter. The Worker's default export is wrapped with `Sentry.withSentry()`, which covers `fetch`, `queue`, and `scheduled` and captures uncaught exceptions and unhandled rejections — including the pre-loop `getAppAccessToken` failure path that [issue #73](https://github.com/antonbsa/twitch-radar/issues/73) identifies as escaping structured logging entirely today.
- **The decisive property is grouping, not delivery.** The incident was not "an error occurred" — it was the same error occurring roughly 10,000 times unobserved. Sentry fingerprints and collapses those into one issue with a counter, and its alert rules can fire only on a newly-seen issue. Reimplementing that deduplication by hand over `KV_APP_CACHE` was the bulk of the alternative design's work, and would have produced a worse version of it with no stack traces and no UI.
- **Slack notification is sent directly from the Worker via a `fetch()` POST to an incoming webhook, not through Sentry's native Slack integration.** Public sources disagree on whether that integration is included in Sentry's free Developer plan (Sentry's own pricing page describes Developer alerting as email-only), and the docs do not state a plan requirement either way. Owning the call removes the dependency on that answer and on any future tier change, keeps working when Sentry is unreachable or its quota is exhausted — precisely when an alert matters most — and costs roughly twenty lines. Slack's Free workspace plan supports incoming webhooks; the relevant caps are 10 installed apps per workspace (a custom webhook app counts as one) and one message per second per channel, neither of which this usage approaches. The division of labour is: **Sentry is the durable record — grouping, stack traces, history, email. Slack is the immediate push, independent of Sentry.**
- **Event volume is controlled structurally, not by random sampling.** `sampleRate` is rejected: uniform random sampling discards the rare, unique error that most needs attention while still letting a repetitive loop consume quota proportionally. Instead, failures inside a scheduled job are **reported to Sentry once per invocation, aggregated**, while the existing per-row `logger.error` calls stay exactly as they are — Workers Logs remains the place for per-row detail. This bounds the EventSub creation job at one Sentry event per minute in the worst case instead of one per failing row per minute. Sentry's **spike protection** (available on all plans) is enabled as the server-side backstop. Per-DSN client-key rate limiting is _not_ available on the free plan (Business/Enterprise only) and is therefore not part of this design.
- **Sentry's `environment` tag is set from `AppConfig.environment`, and alert rules filter on `environment:production`.** Preview reports to Sentry but does not page anyone; its errors are visible when someone looks. `local` never reports at all. **Preview reporting is enabled only after [issue #73](https://github.com/antonbsa/twitch-radar/issues/73) lands and preview's bad `pending` rows are cleaned up** — until then preview would emit roughly 1,440 events per day and exhaust the free plan's 5,000-events-per-month quota within days, before capturing anything of interest.
- **The Sentry DSN and the Slack webhook URL are Worker secrets, optional in the `apps/api/src/env.ts` schema.** An environment without them configured (local dev, a fresh worktree, CI) simply does not report, rather than failing to boot. Alert dispatch is fire-and-forget and must never throw: a failure to deliver an alert cannot be allowed to fail the request, queue message, or scheduled job it was reporting on.

## Consequences

- `@sentry/cloudflare` is the first observability dependency in the repo. [ADR 0040](0040-structured-leveled-logging-convention.md)'s "no third-party logging library" decision is unchanged — `logger.ts` stays a thin custom wrapper and remains the only logging path; Sentry sits alongside it as an error-reporting sink, not as a logging backend.
- `apps/api/wrangler.jsonc` gains `compatibility_flags: ["nodejs_compat"]`. This is a Worker-wide runtime change, not scoped to Sentry, and should be reviewed as such.
- New catch sites must decide explicitly whether they report to Sentry or only log. The default for a per-item failure inside a batch or scheduled loop is **log per item, report once per invocation** — adding a `captureException` inside such a loop reintroduces the volume problem this ADR designs around.
- The free plan's 5,000 events per month is a real ceiling. If aggregate reporting plus spike protection prove insufficient once preview reporting is on, the next lever is narrowing what is reported, not enabling random sampling — and moving to a paid tier is a separate decision.
- If Cloudflare later makes OpenTelemetry export or a Workers error notification available on the Free plan, or the project acquires a custom domain and moves to Workers Paid, the in-Worker SDK approach should be revisited against the platform-native path — as a new ADR superseding this one, not a silent swap.
