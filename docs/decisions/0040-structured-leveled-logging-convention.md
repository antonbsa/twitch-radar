# 0040 - Structured Leveled Logging Convention

## Status

Accepted

## Context

[Issue #19](https://github.com/antonbsa/twitch-radar/issues/19) found that `apps/api/src` had no systematic logging: 12 call sites, all `console.error`/`console.warn` on failure paths only, no shared shape, no severity levels beyond error/warn, and no success/action-tracing logs at all. `apps/api/wrangler.jsonc` had no `observability` block, so nothing a deployed Worker logged was captured anywhere queryable — only visible transiently via `wrangler tail` while attached. `apps/web/src` had one ungated `console.error` call that would print to the browser console in production.

A [follow-up comment on the same issue](https://github.com/antonbsa/twitch-radar/issues/19#issuecomment-5111598831) found a related, deeper problem: even where an error was logged, the detail was already lost before the log call. `TwitchApiError` (`apps/api/src/services/twitch/client.ts`) discarded the failing response's body at all 11 throw sites — the response body is where Twitch explains *why* a request failed (e.g. `{"error":"Bad Request","message":"..."}`) — and `sendWebPush` discarded the push service's rejection body the same way. Separately, every catch site that logged an error did `error instanceof Error ? error.message : String(error)`, dropping `error.stack`, `error.cause`, and any extra fields the error carried (e.g. `TwitchApiError.status`). A structured/leveled logger alone would not have fixed diagnosability here, since the detail was gone one layer earlier.

The implementation spec (`specs/milestones/0-foundations/issue-19-structured-logging.md`) resolved the open design questions the issue left for it: whether to add a dependency or write a thin wrapper, how log level varies by environment, and the Workers Logs sampling rate. This ADR records those as accepted decisions, per [ADR 0001](0001-keep-project-decisions-in-adrs.md).

## Decision

- **`apps/api/src/logger.ts`** is a thin custom wrapper, not a third-party logging library. It exports a singleton `logger` with leveled `debug`/`info`/`warn`/`error` methods, each emitting `JSON.stringify({ level, message, timestamp, ...fields })` via the matching `console.*` method (`console.debug`/`console.log`/`console.warn`/`console.error`), so Cloudflare Workers Logs can auto-extract fields for dashboard filtering. No logging library is a dependency anywhere in the repo, and none of the ~15 call sites this covers justify one — several popular Node loggers assume APIs unavailable in the `workerd` runtime or need a Workers-specific transport, and Workers Logs already does the field extraction a library would otherwise provide.
- **Log level is derived from the existing `AppConfig.environment`**, not a new env var: `logger.configure(environment)` maps `local`/`preview` → `debug` (full detail; preview is low-traffic, noise is cheap) and `production` → `info` (skip debug-level chatter). `configure` is called once per request/queue-message/scheduled invocation, right after `parseEnv`.
- **`apps/api/wrangler.jsonc` has an `observability` block (`{ enabled: true, head_sampling_rate: 1 }`) under `env.production` and `env.preview` only** — not the dev/top-level config, where `wrangler dev`'s terminal already shows `console.*` output directly and Workers Logs' dashboard capture has no value for a process that never leaves the developer's machine. Sampling stays at full capture (`1`) until real production volume is observed; Logpush (external, long-term retention) is out of scope unless a later need for retention beyond Workers Logs' 7-day window arises.
- **`serializeError(error: unknown)`**, also in `logger.ts`, is the shared shape for logging a caught error: `{ error, stack?, cause?, status?, code? }`. It checks for `status`/`code` via `"status" in err` / `"code" in err` rather than importing `TwitchApiError`, so it stays free of a dependency on the Twitch client module and picks up the same fields from any other error shape introduced later. All catch-site log calls spread its result into their fields object instead of the lossy `error instanceof Error ? error.message : String(error)` inline pattern. Serialized string fields (`stack`, `cause`) are truncated to 2000 characters as a safety cap.
- **`TwitchApiError` carries the failing response's body** (`readonly body: string`, alongside the existing `status`), read via `res.text()` at all 11 throw sites in `client.ts` before constructing the error, truncated to 2000 characters. **`sendWebPush`** (`apps/api/src/services/push/web-push.ts`) folds the push service's rejection body into its returned `error` string the same way when `!response.ok`. Neither change alters existing control flow: `TwitchApiError.status` and `WebPushSendResult.endpointGone`/`.ok` still drive all existing branching: `body` and the enriched `error` string are additive diagnostic detail only.
- **`apps/web/src` stays a minimal gate, not a mirrored wrapper.** Its one call site (`context/auth-context.tsx`) is gated behind `import.meta.env.DEV` rather than porting the API's leveled/JSON logger shape to the browser, since no other web-side logging need exists today.

## Consequences

- All `apps/api/src` logging goes through `logger.{debug,info,warn,error}` and `serializeError`, not raw `console.*` calls — new call sites should follow the same convention.
- Adding a third-party structured logging library later (e.g. to send logs to a second destination beyond Workers Logs) supersedes the "thin wrapper" choice here and should be its own ADR, not a silent swap.
- Log level threshold changes only by changing `ENVIRONMENT_MIN_LEVEL` in `logger.ts` or by adopting a per-environment override (e.g. a `LOG_LEVEL` var) later — no such var exists today.
- `TwitchApiError.body` and `sendWebPush`'s enriched error string are available to any caller that wants to surface upstream failure detail (e.g. in future user-facing error messages), not just logs.
- If Workers Logs' 7-day retention or the `head_sampling_rate: 1` default stop being sufficient once real production volume is observed, revisit sampling and/or Logpush adoption as a follow-up decision.
