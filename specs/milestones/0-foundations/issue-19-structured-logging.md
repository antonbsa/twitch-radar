# Issue 19: Structured, Level-Based Logging For Action Tracing

> **Scope update (2026-07-29):** expanded per [issue #19 comment](https://github.com/antonbsa/twitch-radar/issues/19#issuecomment-5111598831) to also fix the upstream cause of several of the diagnosability gaps a logger alone can't solve: `TwitchApiError` and `sendWebPush` both discard the failing response's body before it reaches any log call, and every existing catch site drops `error.stack`/`error.cause`/custom fields (e.g. `.status`) by re-stringifying to `error.message` only. See "Spec Work" and "Implementation Scope" below for the added items.

## Goal

Give the deployed Worker and PWA a shared, leveled logging convention so production issues (EventSub processing, notification matching/delivery, sync/cron runs, token refresh) are diagnosable after the fact, without requiring `wrangler tail` to be attached at the exact moment something happens. This includes making sure the _content_ reaching the logger is actually useful: today several error paths construct an error from only an HTTP status code, discarding the response body where the failing service (Twitch, a push service) explains what went wrong — no logger can surface detail that was already thrown away one layer earlier.

## Grounding

Verified against the worktree at the time this spec was written (all line numbers below match the issue exactly, no drift):

- `apps/api/src`: 12 `console.error`/`console.warn` call sites, zero `console.log`/`info`/`debug` — `http/errors.ts:37`, `index.ts:165,188,198`, `services/twitch/sync.ts:140`, `http/routes/webhooks.ts:106,127`, `services/eventsub/reconcile.ts:86`, `services/twitch/token-refresh.ts:124`, `services/eventsub/subscriptions.ts:52`, `services/notifications/deliver.ts:53,71`.
- `apps/web/src`: one call site, `context/auth-context.tsx:38`, ungated against production.
- No logging utility exists in `apps/api/src` today (no `logger.ts` or equivalent).
- `apps/api/wrangler.jsonc` has no `observability` block at the top level, under `env.production`, or under `env.preview`.
- No structured/leveled logging library is a dependency anywhere in the repo (`apps/api/package.json`, `apps/web/package.json`) — only `hono`, `drizzle-orm`, `nanoid`, `web-push`, `zod` on the API side.
- `apps/api/src/env.ts` already validates and derives `environment: "local" | "preview" | "production"` (from the `ENVIRONMENT` binding) into `AppConfig`, consumed today in `index.ts` (routing the test seam) and elsewhere. This existing field is reused for log-level defaults below rather than introducing a parallel env var.
- `apps/api/src/services/twitch/client.ts`: `TwitchApiError` (`class TwitchApiError extends Error { readonly status: number }`) is thrown from all 11 `if (!res.ok) throw new TwitchApiError(<fixed string>, res.status)` call sites (`exchangeCode`, `refreshAccessToken`, `fetchAppAccessToken`, `createEventsubSubscription`, `getAllEventsubSubscriptions`, `deleteEventsubSubscription`, `getAuthenticatedUser`, `getAllFollowedChannels`, `searchCategories`, `getStreamsByUserIds`, `getAllFollowedStreams`). None of them read `res.text()`/`res.json()` before throwing — the response body (where Twitch's actual error detail lives, e.g. `{"error":"Bad Request","message":"..."}`) is discarded at the point of construction, not at the point of logging.
- `apps/api/src/services/push/web-push.ts`'s `sendWebPush`: on a non-`ok` response it returns `{ ok: false, status: response.status, endpointGone: ..., error: \`Push service responded ${response.status}\` }` — same pattern, the push service's rejection body (invalid VAPID, payload too large, etc.) is never read.
- Every one of the 5 catch sites under Grounding above that log an error (`subscriptions.ts:52`, `reconcile.ts:86`, `token-refresh.ts:124`, `sync.ts:140`, `index.ts:165,188`) builds its logged `error` field as `error instanceof Error ? error.message : String(error)` — this drops `error.stack`, `error.cause`, and any extra fields the error instance carries (e.g. `TwitchApiError.status`), independent of whatever logging mechanism replaces `console.error`.
- `apps/web/src/lib/api.ts`'s `request()` already reads the response body (`res.json().catch(() => null)`) before throwing `ApiRequestError` — confirmed as the reference pattern this spec's `client.ts` fix should mirror on the API side.

## Spec Work

Resolved decisions:

- **Thin custom wrapper, not a third-party logging library.** `apps/api/src/logger.ts` exports leveled functions (`debug`/`info`/`warn`/`error`) that `JSON.stringify` a structured record (`{ level, message, timestamp, ...fields }`) and emit it via the matching `console.*` method (`console.debug`/`console.log`/`console.warn`/`console.error`). Justification: no logging library is a dependency anywhere in the repo today; this is a small single-Worker app with ~12 call sites plus a handful of new ones, not a scale where a dependency (Pino, Winston, etc.) earns its bundle-size and Workers-runtime-compatibility cost (several popular Node loggers assume Node APIs not available in the `workerd` runtime, or need a Workers-specific transport). Workers Logs already auto-extracts fields from a JSON-shaped `console.*` argument, so the wrapper only needs to guarantee that shape — a library adds no capability the wrapper doesn't already cover. Revisit only if a real need emerges (e.g. sending logs to a second destination beyond Workers Logs, at which point Logpush — already called out as future-scope in the issue — is the more likely next step, not a client library swap).
- **Log level is configurable per environment via the existing `environment` config, not a new env var.** The wrapper derives a minimum emit level from `AppConfig.environment` (already parsed in `env.ts`): `local` → `debug` (see everything during local dev), `preview` → `debug` (preview is a low-traffic verification environment; full detail is more useful than saved noise), `production` → `info` (skip debug-level chatter, keep info/warn/error). No new `LOG_LEVEL` var is introduced — it would duplicate an axis the app already models, and nothing in the issue's acceptance criteria requires overriding the level independently of environment. If per-environment overrides are needed later, add an optional `LOG_LEVEL` var then rather than speculatively now.
- **`head_sampling_rate: 1` (full capture) for both `production` and `preview`.** Per the issue's own framing, this should stay at the default until volume is known; there's no existing production traffic data to justify sampling below 1 yet. Revisit once real volume is observed (the issue explicitly leaves this open for a later pass). The `observability` block is added to `env.production` and `env.preview` in `apps/api/wrangler.jsonc`; it is **not** added at the top level (the unnamed/dev environment used by `wrangler dev` and both test tiers) — local dev already sees `console.*` output directly in the terminal running `wrangler dev`, and Workers Logs' dashboard capture has no value for a process that never leaves the developer's machine.
- **ADR required.** This introduces an accepted, code-reflected convention (the wrapper's shape and call sites, the level-per-environment mapping, the `wrangler.jsonc` observability config) per [ADR 0001](../../../docs/decisions/0001-keep-project-decisions-in-adrs.md) — it is a decision the code is expected to follow going forward, not a non-actionable research conclusion, so it belongs in `docs/decisions/`, not a TN. An ADR (next number after 0039) should be added alongside the implementation PR; it is **not** written as part of this spec.
- **Web side stays a minimal gate, not a mirrored wrapper.** `apps/web/src` has exactly one call site and no other logging need identified. Rather than porting the API's `logger.ts` shape (levels, JSON records) to the browser — which nothing here calls for — gate the existing `console.error` in `auth-context.tsx:38` behind `import.meta.env.DEV`. If web-side logging needs grow beyond this single site, a fuller convention can be scoped then.
- **`TwitchApiError` carries the response body.** Add a `body: string` field (read via `res.text()`, since Twitch error bodies are small JSON and a raw string avoids a second parse failure mode) alongside the existing `status`. Every one of the 11 `if (!res.ok) throw new TwitchApiError(...)` sites in `client.ts` becomes `async` at the throw point (they already are `async` functions) — read the body before throwing: `const body = await res.text().catch(() => ""); throw new TwitchApiError(message, res.status, body)`. Truncate to a fixed cap (2000 chars) when constructing the field so a pathological response can't blow up log record size; Twitch error bodies are always small JSON in practice, so this is a safety cap, not an expected path.
- **`sendWebPush` reads the response body on rejection.** In `web-push.ts`, when `!response.ok`, read `await response.text().catch(() => "")` and fold it (truncated the same way) into the returned `error` string, e.g. `` `Push service responded ${response.status}: ${bodyText}` ``. `WebPushSendResult`'s `error` field stays a string (no shape change to the discriminated union) since its two callers (`deliver.ts`) already just log/join it as a string.
- **A shared `serializeError(error: unknown)` helper in `logger.ts`**, used at every catch-site log call instead of the repeated `error instanceof Error ? error.message : String(error)` inline pattern. It returns `{ error: string, stack?: string, cause?: string, status?: unknown, code?: unknown }`: `error.message` (or `String(error)` for non-`Error` throws), `error.stack` when present, `String(error.cause)` when `error.cause !== undefined`, and `status`/`code` when those properties exist on the thrown value (a generic `"status" in error` / `"code" in error` check, not an `instanceof TwitchApiError` import — keeps `logger.ts` free of a dependency on the Twitch client module and also picks up `status/code` from any other error shape the app introduces later). Callers spread its result into their log call's fields object, e.g. `logger.error("EventSub subscription create failed", { subscriptionId: row.id, broadcasterUserId: row.broadcaster_user_id, eventType: row.event_type, ...serializeError(error) })`.

## Implementation Scope

- Add `apps/api/src/logger.ts`: a module exporting `debug`/`info`/`warn`/`error` functions, each accepting `(message: string, fields?: Record<string, unknown>)`, resolving a minimum level from `AppConfig.environment` (see mapping above), and emitting a JSON-stringified `{ level, message, timestamp, ...fields }` record via the corresponding `console.*` method when at or above the resolved minimum level.
- Replace the 12 existing `apps/api/src` `console.error`/`console.warn` call sites listed under Grounding with calls to the new logger, preserving their existing message strings and field payloads (they're already close to the target shape — e.g. `console.error("Twitch event processing failed", { messageId, error })`).
- Add `info`/`debug`-level coverage for currently-unlogged happy-path actions:
  - EventSub processing: a queued Twitch event was processed and whether it produced a state change (`index.ts`, around the `processTwitchEventMessage` call).
  - Notification matching/delivery: a successful send (`deliver.ts`, the `sentSubscriptionId` success path currently has no log at all).
  - Sync/cron runs: scheduled follow sync completion counts (`services/twitch/sync.ts`), EventSub reconciliation run outcome (`services/eventsub/reconcile.ts`), token refresh sweep outcome (`services/twitch/token-refresh.ts`).
  - EventSub webhook notification receipt (`http/routes/webhooks.ts`), not just the ignored/unknown branches.
- Add an `observability` block to `apps/api/wrangler.jsonc` under `env.production` and `env.preview`: `{ "enabled": true, "head_sampling_rate": 1 }`. No change to the top-level (dev) config.
- Gate `apps/web/src/context/auth-context.tsx:38`'s `console.error` behind `import.meta.env.DEV`.
- Add `serializeError(error: unknown)` to `apps/api/src/logger.ts` (see Spec Work) and replace the manual `error instanceof Error ? error.message : String(error)` field construction at all 5 existing catch sites (`subscriptions.ts:52`, `reconcile.ts:86`, `token-refresh.ts:124`, `sync.ts:140`, `index.ts:165,188`) with `...serializeError(error)`, plus any new catch sites added for the happy-path coverage above that also handle errors.
- `apps/api/src/services/twitch/client.ts`: add `body: string` to `TwitchApiError`, and update all 11 `if (!res.ok) throw new TwitchApiError(...)` sites to read and pass the (truncated) response body first.
- `apps/api/src/services/push/web-push.ts`: update `sendWebPush`'s non-`ok` branch to read and fold the (truncated) response body text into the returned `error` string.
- Document the logging convention (wrapper usage, level-per-environment mapping, error-serialization shape) — pending the ADR called out above; this spec's implementation should reference that ADR number once written.

## Acceptance Criteria

- [ ] `apps/api/wrangler.jsonc` has an `observability` block (`enabled: true`, `head_sampling_rate: 1`) under both `env.production` and `env.preview`; no block at the top level.
- [ ] `apps/api/src/logger.ts` exists, exporting leveled (`debug`/`info`/`warn`/`error`) functions that emit structured JSON via `console.*`, with the minimum emitted level derived from `AppConfig.environment` (`local`/`preview` → `debug`, `production` → `info`).
- [ ] All 12 existing `apps/api/src` call sites listed under Grounding use the new logger instead of raw `console.*`.
- [ ] New `info`/`debug` coverage exists for: EventSub event processing, notification match/delivery success, scheduled sync/reconcile/token-refresh run outcomes, EventSub webhook notification receipt.
- [ ] API logs are JSON-shaped so Workers Logs can auto-extract fields for dashboard filtering.
- [ ] `apps/web/src/context/auth-context.tsx`'s `console.error` is gated behind `import.meta.env.DEV`; verified by inspecting the production build output (`npm run build` in `apps/web`, confirm the gate survives minification) and/or the browser console on a deployed production build.
- [ ] Cloudflare dashboard (Workers Logs) is confirmed to show captured logs for a real request/event in at least one deployed environment (production or preview), after `wrangler deploy`.
- [ ] An ADR documenting the logging convention (wrapper shape, level-per-environment mapping, `head_sampling_rate` choice, error-serialization shape) is added to `docs/decisions/`, referenced from this spec.
- [ ] `TwitchApiError` carries the failing response's body (truncated), and all 11 throw sites in `apps/api/src/services/twitch/client.ts` populate it.
- [ ] `sendWebPush` (`apps/api/src/services/push/web-push.ts`) includes the push service's rejection response body (truncated) in its returned `error` string when `!response.ok`.
- [ ] `apps/api/src/logger.ts` exports `serializeError(error: unknown)`, and all 5 existing catch-site log calls (plus any new ones from the happy-path coverage work) use it instead of inline `error instanceof Error ? error.message : String(error)`, so logged records include `stack`/`cause`/`status`/`code` when the thrown value carries them.
- [ ] A local repro (e.g. `createEventsubSubscription` failing against a non-public `PUBLIC_URL` in dev) surfaces Twitch's actual rejection message in the log output, not just the fixed string + status code.

## Completion Validation

- `apps/api` typecheck/build passes with the new `logger.ts` and updated call sites.
- `tests/api` suite passes unchanged (no behavioral change to error handling, only log emission and error-detail enrichment — `TwitchApiError`/`WebPushSendResult` callers that only branch on `.status`/`.ok`/`.endpointGone` are unaffected by the added `body`/richer `error` string).
- Manual: deploy to `preview` or `production`, trigger a real request/event, confirm the Cloudflare dashboard's Workers Logs Query Builder shows the emitted structured log with filterable fields.
- Manual: build `apps/web` for production (`npm run build`), serve/inspect the bundle or a deployed instance, and confirm no `console.*` output appears from `auth-context.tsx` when hitting the `/me` 401 or failure path.
- Manual: force a Twitch API rejection locally (e.g. attempt EventSub subscription creation with a non-HTTPS/non-public `PUBLIC_URL`) and confirm the resulting log record includes Twitch's actual error body, not just `"EventSub subscription create failed"` + a status code.

## Dependencies

None — this is infrastructure/observability work layered onto existing call sites; no other milestone-0 spec blocks it.
