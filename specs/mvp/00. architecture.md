# MVP Architecture

## Purpose

This document is the active MVP product and system specification.

Decision documentation policy: [ADR 0001](../../docs/decisions/0001-keep-project-decisions-in-adrs.md).

## Goal

Build a mobile-first PWA where a user connects their Twitch account, chooses categories they care about, and receives push notifications when followed streamers start streaming those categories or switch into those categories while live.

## Product Requirements

- User can connect their Twitch account.
- User can sync followed Twitch channels.
- User can see followed channels ordered like Twitch's sidebar:
  - live channels first
  - live channels ordered by viewer count descending
  - offline channels below
- User can choose notification categories:
  - per followed channel
  - globally across followed channels
- User receives a PWA/Web Push notification when:
  - a followed channel starts streaming in a desired category
  - a followed channel switches into a desired category while live

## Core Data Contracts

The durable schema is represented by D1 migrations in [../../infra/migrations](../../infra/migrations).

Core entities:

- `users`: Local app user records tied to Twitch identity. Created or updated during Twitch OAuth callback and used as the owner for preferences, tokens, follows, push subscriptions, and deliveries.
- `twitch_tokens`: User Twitch access and refresh tokens, scopes, and expiry metadata used for Twitch API calls, token refresh, and follow sync.
- `push_subscriptions`: Browser/PWA Push API subscriptions for authenticated users. Used to send Web Push notifications and track revoked or invalid endpoints.
- `followed_channels`: Per-user snapshot of followed Twitch broadcasters, populated by follow sync and used to render the followed-channel list.
- `monitored_channels`: Global set of unique broadcasters that require backend EventSub monitoring because at least one active preference depends on them.
- `eventsub_subscriptions`: Local records of Twitch EventSub webhook subscriptions for monitored broadcasters, used for creation, status tracking, and reconciliation.
- `channel_state`: Current snapshot of each monitored broadcaster's live/offline stream state, category, stream metadata, and last update time. This is the current-state source of truth.
- `channel_state_changes`: Relevant state transition history for monitored broadcasters, used for audit, dedupe, and notification matching inputs. It is not the current-state source of truth.
- `channel_category_preferences`: Per-user, per-broadcaster category notification preferences for specific followed channels.
- `global_category_preferences`: Per-user category notification preferences that apply across the user's followed channels.
- `notification_deliveries`: Notification send attempt records and delivery status, including dedupe keys for user, broadcaster, category, stream, and trigger type.

## User OAuth And Sync Flow

### 1. User Starts Twitch Login

The PWA calls:

```txt
GET /api/auth/twitch/start
```

### 2. OAuth Callback

Twitch redirects to:

```txt
GET /api/auth/twitch/callback?code=...&state=...
```

The Worker:

1. Validates `state`.
2. Exchanges the code for tokens.
3. Fetches the Twitch user profile.
4. Creates or updates `users`.
5. Stores tokens in `twitch_tokens`.
6. Starts followed-channel sync.

### 3. Followed Channel Sync

The sync path updates `followed_channels` and available live metadata for the authenticated user.

## Preference Selection Flow

### Per-Channel Category Preference

When a user selects a category for a specific followed channel, the app stores a `channel_category_preferences` row and ensures the broadcaster can be monitored.

### Global Category Preference

When a user selects a global category, the app stores a `global_category_preferences` row and ensures followed broadcasters can be monitored.

## Event Processing Flow

### Webhook Entry Point

Twitch sends webhook requests to:

```txt
POST /api/webhooks/twitch/eventsub
```

### Queue Processing

Queued Twitch events update current channel state, record relevant state changes, match preferences, create notification delivery records, and send Web Push notifications when applicable.

## PWA Notification Flow

### Subscribe Device

1. PWA registers service worker.
2. User grants notification permission.
3. PWA creates Push API subscription with VAPID public key.
4. PWA sends subscription to:

```txt
POST /api/push-subscriptions
```

5. Worker stores it in `push_subscriptions`.

### Send Notification

When a Twitch event matches preferences:

1. Worker or queue consumer finds active push subscriptions for the user.
2. Worker sends Web Push payload to each subscription endpoint.
3. Browser push service delivers the message to the device.
4. Service worker receives `push`.
5. Service worker calls `showNotification`.

Payload shape:

```json
{
  "title": "Alanzoka is streaming Software and Game Development",
  "body": "Alanzoka just started streaming a category you follow.",
  "url": "/channels/alanzoka"
}
```

## API Surface

MVP API:

```txt
GET  /api/auth/twitch/start
GET  /api/auth/twitch/callback
POST /api/auth/logout

GET  /api/me
POST /api/sync/follows

GET  /api/channels/followed
GET  /api/categories/search?q=...

GET  /api/preferences
POST /api/preferences/channel
DELETE /api/preferences/channel/:id
POST /api/preferences/global
DELETE /api/preferences/global/:id

GET  /api/push/vapid-public-key
POST /api/push-subscriptions
DELETE /api/push-subscriptions/:id

POST /api/webhooks/twitch/eventsub
```

## Background Jobs

### Follow Sync Job

Runs after OAuth connection, on user request, and periodically for active users.

Responsibilities:

- Refresh Twitch token if needed.
- Sync followed channels.
- Update live followed subset.
- Ensure monitored broadcasters are current for saved preferences.

### EventSub Reconciliation Job

Runs periodically.

Responsibilities:

- Reconcile local EventSub records with Twitch.
- Recreate missing subscriptions.
- Mark revoked or failed subscriptions.
- Remove subscriptions for broadcasters no longer needed.

### Token Refresh Job

Runs on-demand before Twitch API calls and periodically for active users.

Responsibilities:

- Refresh expired user access tokens.
- Mark users requiring reconnect if refresh fails.

## MVP Implementation Phases

### Phase 1: Auth And PWA Shell

- Twitch OAuth.
- User session.
- Push subscription registration.
- Basic followed-channel sync.
- Followed-channel list UI.

### Phase 2: Preferences

- Search/select categories.
- Per-channel preferences.
- Global category preferences.
- Preference management UI.

### Phase 3: EventSub

- EventSub subscription management.
- Webhook signature handling.
- Callback verification challenge.
- Queue incoming events.
- Reconcile EventSub subscription state.

### Phase 4: State And Matching

- Seed current channel state.
- Process stream/category/offline events.
- Compare previous and next state.
- Store relevant state changes.

### Phase 5: Notification Delivery

- Match per-channel and global preferences.
- Create notification delivery records.
- Send Web Push.
- Handle invalid push subscriptions.
- Add deduplication and retries.

## Key Risks

- EventSub subscription count grows with unique monitored broadcasters.
- Global category preferences may require broad monitoring.
- Users can follow many channels, so sync and subscription creation need pagination and rate-limit handling.
- Twitch tokens require refresh and protection.
- Push subscriptions can expire or be revoked.
- iOS PWA notifications require the installed Home Screen app path.
- Webhook processing can receive retries.
