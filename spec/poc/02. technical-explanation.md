# Technical Explanation

## What This POC Proves

This POC proves that a backend can send a Web Push notification to an installed PWA after an external event happens.

For this simplified version, the external event is simulated by a backend timer:

1. The user selects a predefined channel such as `Alanzoka (15s)`.
2. The backend stores a waiting notification.
3. The backend starts a timer for 15 seconds.
4. When the timer fires, the backend sends a Web Push message.
5. The browser push service delivers that message to the PWA service worker.
6. The service worker displays the notification on the device.

There is no Twitch integration in this POC. Twitch is intentionally replaced by fixed channel options and backend timers.

## Package Responsibilities

### Runtime Dependencies

#### `fastify`

Fastify is the HTTP server framework.

It is responsible for:

- Starting the backend server.
- Defining API routes.
- Parsing JSON request bodies.
- Sending JSON responses.
- Logging requests.

It was chosen because it is lightweight, fast, and has a small API surface. For this POC, Express would also work, but Fastify gives good request validation ergonomics and clear route structure without much boilerplate.

Used in:

- `src/server.ts`

#### `@fastify/static`

This package serves files from the `public/` directory.

It is responsible for serving:

- `public/index.html`
- `public/app.js`
- `public/styles.css`
- `public/manifest.webmanifest`
- `public/service-worker.js`
- `public/icon.svg`

It was chosen because the PWA should be served from the same origin as the API. Same-origin serving avoids extra CORS complexity and keeps service worker scope simple.

Used in:

- `src/server.ts`

#### `web-push`

This is the Web Push sender library.

It is responsible for:

- Configuring VAPID identity.
- Encrypting push payloads.
- Sending push requests to browser push service endpoints.
- Generating VAPID key pairs through the CLI command.

It was chosen because implementing the Web Push protocol manually is unnecessary and error-prone. The protocol requires payload encryption and correctly signed VAPID headers. `web-push` handles those details.

Used in:

- `src/push.ts`
- `npm run vapid`

#### `zod`

Zod validates request payloads and query strings.

It is responsible for validating:

- Push subscription request bodies.
- Notification scheduling request bodies.
- Notification list query parameters.

It was chosen because this POC accepts browser-provided data and stores it locally. Runtime validation keeps malformed data out of the JSON files and gives predictable `400` responses.

Used in:

- `src/server.ts`

#### `nanoid`

Nano ID generates compact unique IDs.

It is responsible for creating:

- Push subscription IDs.
- Notification IDs.

It was chosen because it is small, URL-safe, and simpler than UUIDs for this POC.

Used in:

- `src/notifications.ts`

## Source File Responsibilities

### `src/server.ts`

This is the application entrypoint.

It does four main things:

1. Loads environment variables.
2. Configures Web Push with VAPID keys.
3. Registers the static PWA files.
4. Defines the API routes.

The API routes are:

- `GET /api/config`
- `POST /api/push-subscriptions`
- `POST /api/notifications`
- `GET /api/notifications?subscriptionId=...`

It also calls `hydrateNotificationTimers()` on startup so waiting notifications stored in JSON are scheduled again after a server restart.

### `src/channels.ts`

Contains the five predefined channel fixtures.

Each channel has:

- `id`
- `label`
- `delaySeconds`

Example:

```ts
{ id: "alanzoka-15", label: "Alanzoka", delaySeconds: 15 }
```

These replace real Twitch events in the POC.

### `src/storage.ts`

Provides small JSON file storage helpers.

It is responsible for:

- Creating the `data/` directory when needed.
- Reading JSON collections.
- Writing JSON collections.
- Writing through a temporary file and then renaming it.

The temp-file rename flow reduces the chance of leaving a partially written JSON file if the process is interrupted during a write.

### `src/push.ts`

Wraps Web Push configuration and sending.

It is responsible for:

- Reading VAPID config from environment variables.
- Calling `webPush.setVapidDetails(...)`.
- Sending push payloads through `webPush.sendNotification(...)`.

The backend does not send notifications directly to the phone. It sends the encrypted push message to the endpoint stored in the browser's push subscription.

### `src/notifications.ts`

This contains the POC notification domain logic.

It is responsible for:

- Creating or updating push subscription records.
- Creating notification records.
- Scheduling timers.
- Rehydrating waiting timers on startup.
- Sending Web Push messages when timers fire.
- Marking notifications as `triggered` or `failed`.
- Sorting waiting notifications before old notifications.

This is where the simulated external event currently lives. In a future Twitch-backed version, Twitch EventSub handlers would eventually call into similar notification creation/sending logic.

### `public/index.html`

Defines the mobile UI structure.

It contains:

- App header.
- Notification enable/status section.
- Channel select input.
- Schedule button.
- Waiting notification list.
- Triggered notification list.

### `public/app.js`

This is the browser-side app controller.

It is responsible for:

- Loading config from the backend.
- Rendering the predefined channel options.
- Registering the service worker.
- Requesting notification permission.
- Creating the Push API subscription.
- Sending the subscription to the backend.
- Scheduling notifications through the API.
- Polling notification status.
- Rendering waiting and triggered lists.

### `public/service-worker.js`

This is the PWA background worker.

It is responsible for:

- Receiving `push` events.
- Reading the push payload.
- Calling `self.registration.showNotification(...)`.
- Handling notification clicks.
- Focusing an existing app window or opening `/`.

This file is essential. Without a service worker, the browser has no background script that can receive push messages while the page is closed.

### `public/manifest.webmanifest`

Defines installable PWA metadata.

It is responsible for:

- App name.
- Short name.
- Start URL.
- Display mode.
- Theme/background colors.
- Icons.

On iOS, the PWA must be added to the Home Screen to validate the intended installed-PWA push behavior.

## VAPID Keys

VAPID stands for Voluntary Application Server Identification.

The backend uses VAPID keys to identify itself to push services. The key pair has two parts:

- Public key: sent to the browser so it can create a push subscription for this application server.
- Private key: kept on the backend and used by `web-push` to sign outgoing push requests.

The public key is safe to expose to the frontend. The private key must stay server-side.

In this app:

- `GET /api/config` returns `vapidPublicKey`.
- `public/app.js` passes that public key into `pushManager.subscribe(...)`.
- `src/push.ts` uses the private key when sending notifications.

Generate keys with:

```sh
npm run vapid
```

Then put them in `.env`:

```env
VAPID_PUBLIC_KEY=...
VAPID_PRIVATE_KEY=...
VAPID_SUBJECT=mailto:dev@example.com
```

## Full Subscription Flow

### 1. User Opens The App

The user loads the PWA from the backend origin.

For local desktop testing:

```txt
http://localhost:3000
```

For iPhone testing, this must be HTTPS:

```txt
https://your-tunnel-url.example
```

The same origin serves both:

- Static frontend files.
- Backend API routes.

### 2. Frontend Loads Runtime Config

`public/app.js` calls:

```txt
GET /api/config
```

The backend returns:

```json
{
  "vapidPublicKey": "...",
  "channels": [
    {
      "id": "alanzoka-15",
      "label": "Alanzoka",
      "delaySeconds": 15
    }
  ]
}
```

The frontend uses this to:

- Populate the channel select input.
- Store the VAPID public key for Push API subscription.

### 3. Frontend Registers The Service Worker

The browser runs:

```js
navigator.serviceWorker.register("/service-worker.js");
```

This creates a background-capable service worker for the origin.

The service worker scope is `/`, meaning it can receive push events for the whole app.

### 4. User Taps Enable Notifications

The app calls:

```js
Notification.requestPermission();
```

This must happen from a user gesture. Browsers do not allow arbitrary background permission prompts.

Possible results:

- `granted`
- `denied`
- `default`

Only `granted` lets the app continue to Push API subscription.

### 5. Browser Creates A Push Subscription

After permission is granted, the app calls:

```js
registration.pushManager.subscribe({
  userVisibleOnly: true,
  applicationServerKey: vapidPublicKey,
});
```

This asks the browser to create a Push API subscription.

The resulting subscription contains:

- `endpoint`
- `keys.p256dh`
- `keys.auth`

The endpoint is a URL owned by the browser vendor's push service, not by this app.

Examples:

- Chrome uses a Google push service endpoint.
- Safari/iOS uses Apple's push infrastructure.

The keys are used so the backend can encrypt payloads for that specific subscription.

### 6. Frontend Sends Subscription To Backend

The frontend sends:

```txt
POST /api/push-subscriptions
```

With a body like:

```json
{
  "subscription": {
    "endpoint": "https://...",
    "keys": {
      "p256dh": "...",
      "auth": "..."
    }
  }
}
```

The backend validates this with Zod.

Then `src/notifications.ts` stores it as a `PushSubscriptionRecord` in:

```txt
data/subscriptions.json
```

The backend returns:

```json
{
  "subscriptionId": "..."
}
```

The browser stores that ID in `localStorage`.

This ID is not a security mechanism. It is just the POC's way to associate scheduled notifications with this browser subscription.

## Full Scheduling Flow

### 1. User Selects A Channel

The user selects one of the predefined channel options:

```txt
Alanzoka (15s)
```

The frontend stores:

```js
state.selectedChannelId = "alanzoka-15";
```

The schedule button is enabled only when:

- Push is supported.
- Notification permission is granted.
- A push subscription was saved.
- A channel is selected.

### 2. User Taps Schedule Notification

The frontend sends:

```txt
POST /api/notifications
```

With:

```json
{
  "subscriptionId": "...",
  "channelId": "alanzoka-15"
}
```

### 3. Backend Creates A Waiting Notification

`src/notifications.ts` does this:

1. Loads subscriptions from `data/subscriptions.json`.
2. Confirms the `subscriptionId` exists.
3. Looks up the channel fixture from `src/channels.ts`.
4. Calculates `scheduledFor`.
5. Creates a `NotificationRecord`.
6. Saves it to `data/notifications.json`.
7. Starts a `setTimeout(...)`.

The stored record looks like:

```json
{
  "id": "...",
  "subscriptionId": "...",
  "channelId": "alanzoka-15",
  "channelLabel": "Alanzoka",
  "delaySeconds": 15,
  "status": "waiting",
  "createdAt": "2026-06-21T20:30:00.000Z",
  "scheduledFor": "2026-06-21T20:30:15.000Z",
  "triggeredAt": null
}
```

### 4. Frontend Shows The Waiting Item

The frontend polls:

```txt
GET /api/notifications?subscriptionId=...
```

The backend returns notifications sorted as:

1. Waiting notifications first, soonest scheduled first.
2. Triggered or failed notifications below, newest first.

The frontend renders waiting notifications in the `Waiting` section.

## Full Firing Flow

### 1. Backend Timer Fires

When `setTimeout(...)` fires, `triggerNotification(notificationId)` runs.

It:

1. Loads current notifications.
2. Loads current subscriptions.
3. Finds the matching waiting notification.
4. Finds the matching push subscription.
5. Sends a Web Push payload.

### 2. Backend Sends Web Push

The backend calls:

```ts
webPush.sendNotification(subscription, JSON.stringify(payload));
```

The payload is:

```json
{
  "title": "Alanzoka is live",
  "body": "Test notification fired after 15 seconds.",
  "url": "/"
}
```

`web-push` then:

1. Encrypts the payload for the subscription.
2. Signs the request with VAPID.
3. Sends the request to the subscription endpoint.

The request does not go directly to the phone. It goes to the browser vendor's push service.

### 3. Browser Push Service Delivers The Message

The push service receives the encrypted push message.

Then it routes the message to the target browser/device associated with the subscription.

On iPhone, the intended POC path is:

1. The user has opened the app from HTTPS.
2. The user has added the PWA to the Home Screen.
3. The user has granted notification permission.
4. The installed PWA has an active push subscription.
5. Apple's push infrastructure delivers the message to the installed web app.

### 4. Service Worker Receives The Push Event

The browser wakes the service worker and dispatches:

```js
self.addEventListener("push", ...)
```

The service worker reads:

```js
event.data.json();
```

Then it shows the notification:

```js
self.registration.showNotification(payload.title, {
  body: payload.body,
  icon: "/icon.svg",
  badge: "/icon.svg",
  data: {
    url: payload.url || "/",
  },
});
```

This is what creates the visible mobile notification.

### 5. Backend Marks Notification As Triggered

If `webPush.sendNotification(...)` succeeds, the backend updates the notification:

```json
{
  "status": "triggered",
  "triggeredAt": "..."
}
```

If sending fails, it updates:

```json
{
  "status": "failed",
  "errorMessage": "..."
}
```

### 6. Frontend Moves Item To Triggered

The frontend keeps polling:

```txt
GET /api/notifications?subscriptionId=...
```

After the backend marks the notification as `triggered`, the frontend receives the updated record and renders it in the muted `Triggered` section.

This list update is separate from the mobile notification display. The visible mobile notification is caused by the service worker. The UI list changes because the page polls the backend.

## Notification Click Flow

When the user taps the notification, the browser dispatches:

```js
self.addEventListener("notificationclick", ...)
```

The service worker:

1. Closes the notification.
2. Checks for an existing app window.
3. Focuses it if found.
4. Otherwise opens `/`.

This is implemented in:

```txt
public/service-worker.js
```

## Why The Backend Is Required

A browser cannot schedule a reliable future push notification by itself.

The backend is required because:

- Push subscriptions must be stored somewhere outside the browser.
- External events happen outside the user's device.
- The app must send a push request even when the PWA is closed.
- Web Push messages are sent from an application server to a browser push service.

In this POC, the backend timer simulates the external event. In the future Twitch version, Twitch EventSub would replace the timer as the event source.

## Restart Behavior

On startup, the backend calls:

```ts
hydrateNotificationTimers();
```

It reads `data/notifications.json`, finds waiting notifications, and schedules timers again.

If a waiting notification is already past its scheduled time when the server starts, the current implementation schedules it with a zero millisecond delay. That means it will attempt to send immediately.

## Important iPhone Constraints

For the intended iPhone PWA test:

- The app must be served over HTTPS.
- The app should be added to the Home Screen.
- Permission must be granted from a user gesture.
- The installed PWA must create the push subscription.
- The backend must remain running until the timer fires.
- The HTTPS tunnel URL should stay stable during the test.

Desktop `localhost` is useful for development, but it does not prove the final iPhone installed-PWA behavior.

## End-To-End Sequence

```text
User opens PWA
  -> frontend fetches /api/config
  -> frontend registers service worker

User taps Enable notifications
  -> browser asks for permission
  -> frontend creates Push API subscription
  -> frontend POSTs subscription to backend
  -> backend stores subscription in data/subscriptions.json
  -> backend returns subscriptionId
  -> frontend stores subscriptionId in localStorage

User selects Alanzoka (15s)
  -> frontend enables Schedule button

User taps Schedule notification
  -> frontend POSTs subscriptionId + channelId
  -> backend validates request
  -> backend creates waiting notification
  -> backend stores it in data/notifications.json
  -> backend starts setTimeout for 15 seconds
  -> frontend polls and shows item in Waiting

Timer fires
  -> backend finds notification and subscription
  -> backend sends encrypted Web Push payload with VAPID
  -> browser push service receives the push request
  -> browser push service delivers it to the device
  -> service worker receives push event
  -> service worker calls showNotification
  -> mobile OS displays notification
  -> backend marks notification as triggered
  -> frontend polling moves item to Triggered

User taps notification
  -> service worker receives notificationclick
  -> service worker focuses existing app window or opens /
```

## Current Limitations

- There is no authentication.
- `subscriptionId` is stored in `localStorage`.
- There is no unsubscribe endpoint.
- There is no cleanup for expired subscriptions.
- There is no retry queue for failed push sends.
- JSON storage is not concurrency-safe enough for production.
- Timers run in a single Node.js process.
- Multiple backend instances would duplicate or lose timer ownership.
- The app does not currently include real Twitch events.

These are acceptable for the POC because the current goal is only to validate Web Push notification delivery to an installed PWA.
