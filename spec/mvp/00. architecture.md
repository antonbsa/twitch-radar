# MVP Architecture

## Goal

Build a mobile-first PWA where a user connects their Twitch account, chooses categories they care about, and receives push notifications when followed streamers start streaming those categories or switch into those categories while live.

The notification mechanism proved in the POC remains the delivery layer. The MVP replaces the POC timer with Twitch EventSub webhook events and durable serverless processing.

## Requirements

### Product Features

- User can connect their Twitch account.
- User can sync followed Twitch channels.
- User can see followed channels ordered like Twitch's sidebar:
  - live channels first
  - live channels ordered by viewer count descending
  - offline channels below
- User can choose notification categories:
  - per followed channel
  - globally, meaning any followed channel streaming that category should notify
- User receives a PWA/Web Push notification when:
  - a followed channel starts streaming in a desired category
  - a followed channel switches into a desired category while live

### Technical Requirements

- Use Twitch EventSub webhooks, not EventSub WebSockets.
- Store current channel state because EventSub payloads represent current event data, not a full previous/current diff model.
- Store relevant channel state changes for auditing and deduplication.
- Store user preferences and push subscriptions durably.
- Do not rely on `setTimeout`, process memory, local files, or an always-running backend.

## Validated Twitch Constraints

### Serverless Listener Feasibility

Twitch EventSub supports webhook transport. With webhooks, Twitch sends HTTPS requests to the app when subscribed events occur. This fits serverless functions/workers because the app only needs to handle inbound HTTP requests.

EventSub WebSockets are not recommended for this MVP because they require a persistent connection to Twitch. Persistent WebSocket clients do not fit typical serverless request lifecycles.

Recommended transport:

```txt
EventSub Webhook
```

Avoid for serverless:

```txt
EventSub WebSocket
```

Sources:

- https://dev.twitch.tv/docs/eventsub/
- https://dev.twitch.tv/docs/eventsub/handling-webhook-events/
- https://dev.twitch.tv/docs/eventsub/handling-websocket-events/

### EventSub Webhook Security

Webhook messages must be verified using Twitch's HMAC-SHA256 signature.

The webhook handler must verify:

- `Twitch-Eventsub-Message-Id`
- `Twitch-Eventsub-Message-Timestamp`
- `Twitch-Eventsub-Message-Signature`
- raw request body
- subscription secret

Webhook handlers should respond quickly. If additional work is needed, the handler should enqueue the event and return a `2XX` response.

Source:

- https://dev.twitch.tv/docs/eventsub/handling-webhook-events/

### Followed Channel Data

To sync followed channels, use Twitch user OAuth with:

```txt
user:read:follows
```

Relevant APIs:

- `GET /helix/channels/followed`
- `GET /helix/streams/followed`

Use `Get Followed Channels` for the full followed-channel list. Use `Get Followed Streams` for the live subset with live metadata such as viewer count and category/game. Merge both datasets to render the sidebar-style list.

Sources:

- https://dev.twitch.tv/docs/api/reference/#get-followed-channels
- https://dev.twitch.tv/docs/api/reference/#get-followed-streams
- https://dev.twitch.tv/docs/authentication/scopes/

### Event Types Needed

Use these EventSub event types for monitored broadcasters:

```txt
stream.online
stream.offline
channel.update
```

Purpose:

- `stream.online`: broadcaster started streaming.
- `stream.offline`: broadcaster stopped streaming.
- `channel.update`: broadcaster changed channel properties, including category.

`stream.online` is not enough by itself because category matching requires knowing the stream/category at or shortly after the online event. `channel.update` is not enough by itself because a broadcaster can start already in the target category without changing category after going live.

Sources:

- https://dev.twitch.tv/docs/eventsub/eventsub-subscription-types/#streamonline
- https://dev.twitch.tv/docs/eventsub/eventsub-subscription-types/#streamoffline
- https://dev.twitch.tv/docs/eventsub/eventsub-subscription-types/#channelupdate

## Recommended Platform Architecture

Use Cloudflare's serverless stack:

```txt
Cloudflare Pages
  -> hosts the PWA static app

Cloudflare Workers
  -> OAuth callback
  -> API routes
  -> Twitch EventSub webhook receiver
  -> Web Push sender

Cloudflare Queues
  -> async Twitch event processing
  -> notification send jobs

Cloudflare D1
  -> relational durable storage

Cloudflare KV
  -> short-lived cache and app access token cache

Cloudflare Secrets
  -> Twitch client secret
  -> EventSub webhook secret
  -> VAPID private key
```

This avoids an always-running server while still supporting Twitch webhooks and push notification delivery.

## Why Serverless Fits The MVP

The backend does not need to keep listening through a persistent process if Twitch EventSub webhooks are used.

The app needs durable request handlers and queues:

- Twitch calls the webhook URL when events happen.
- The Worker verifies the webhook and enqueues the event.
- A queue consumer processes the event and sends notifications.
- D1 stores all state needed for comparison, preference matching, and deduplication.

This is a good serverless fit.

What would not fit:

- EventSub WebSocket listener on a serverless function.
- In-memory channel state.
- Local JSON files.
- Delayed work based on `setTimeout`.

## Core Data Model

The initial thought of having a subscriptions table and a channel updates table is directionally right, but too broad. The MVP needs separate tables because there are several different subscription concepts:

- Twitch EventSub subscriptions.
- Browser push subscriptions.
- User category notification preferences.

It also needs a current state table in addition to a history/update table. The current state table is required for comparisons. The history table can store only relevant changes.

### `users`

Stores one row per connected Twitch user.

```sql
CREATE TABLE users (
  id TEXT PRIMARY KEY,
  twitch_user_id TEXT NOT NULL UNIQUE,
  twitch_login TEXT NOT NULL,
  twitch_display_name TEXT NOT NULL,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  last_follow_sync_at TEXT
);
```

### `twitch_tokens`

Stores OAuth tokens for the user.

```sql
CREATE TABLE twitch_tokens (
  user_id TEXT PRIMARY KEY REFERENCES users(id),
  access_token TEXT NOT NULL,
  refresh_token TEXT NOT NULL,
  expires_at TEXT NOT NULL,
  scopes TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
```

Production note: tokens should be encrypted before storage. Cloudflare Worker secrets should hold the encryption key.

### `push_subscriptions`

Stores browser Push API subscriptions.

```sql
CREATE TABLE push_subscriptions (
  id TEXT PRIMARY KEY,
  user_id TEXT NOT NULL REFERENCES users(id),
  endpoint TEXT NOT NULL UNIQUE,
  p256dh TEXT NOT NULL,
  auth TEXT NOT NULL,
  user_agent TEXT,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  revoked_at TEXT
);
```

A user may have multiple push subscriptions across devices/browsers.

### `followed_channels`

Stores the user's followed-channel relationship and lightweight display cache.

```sql
CREATE TABLE followed_channels (
  user_id TEXT NOT NULL REFERENCES users(id),
  broadcaster_user_id TEXT NOT NULL,
  broadcaster_login TEXT NOT NULL,
  broadcaster_display_name TEXT NOT NULL,
  broadcaster_profile_image_url TEXT,
  followed_at TEXT,
  last_synced_at TEXT NOT NULL,
  PRIMARY KEY (user_id, broadcaster_user_id)
);
```

### `monitored_channels`

Stores unique broadcasters that at least one user currently needs monitored.

This prevents duplicate EventSub subscriptions when many users follow the same broadcaster.

```sql
CREATE TABLE monitored_channels (
  broadcaster_user_id TEXT PRIMARY KEY,
  broadcaster_login TEXT,
  broadcaster_display_name TEXT,
  monitor_reason TEXT NOT NULL,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  disabled_at TEXT
);
```

### `eventsub_subscriptions`

Stores Twitch EventSub subscriptions created by the app.

```sql
CREATE TABLE eventsub_subscriptions (
  id TEXT PRIMARY KEY,
  twitch_subscription_id TEXT UNIQUE,
  broadcaster_user_id TEXT NOT NULL,
  event_type TEXT NOT NULL,
  event_version TEXT NOT NULL,
  status TEXT NOT NULL,
  callback_url TEXT NOT NULL,
  secret_version TEXT NOT NULL,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  revoked_at TEXT,
  UNIQUE (broadcaster_user_id, event_type, event_version)
);
```

Expected event types:

- `stream.online`
- `stream.offline`
- `channel.update`

### `channel_state`

Stores the latest known state for each monitored broadcaster.

This table is required because EventSub events do not provide a reliable full previous-state diff for this app's matching rules.

```sql
CREATE TABLE channel_state (
  broadcaster_user_id TEXT PRIMARY KEY,
  is_live INTEGER NOT NULL DEFAULT 0,
  stream_id TEXT,
  category_id TEXT,
  category_name TEXT,
  title TEXT,
  viewer_count INTEGER,
  started_at TEXT,
  updated_from_event_at TEXT,
  updated_at TEXT NOT NULL
);
```

Use this table to decide:

- live changed from false to true
- live changed from true to false
- category changed from one category to another
- category changed into a desired category
- category changed out of a desired category

### `channel_state_changes`

Stores relevant state transitions only.

This table should not be the only source of current state. It is an audit/deduplication/history table.

```sql
CREATE TABLE channel_state_changes (
  id TEXT PRIMARY KEY,
  broadcaster_user_id TEXT NOT NULL,
  eventsub_message_id TEXT NOT NULL UNIQUE,
  change_type TEXT NOT NULL,
  previous_is_live INTEGER,
  next_is_live INTEGER,
  previous_category_id TEXT,
  previous_category_name TEXT,
  next_category_id TEXT,
  next_category_name TEXT,
  stream_id TEXT,
  occurred_at TEXT NOT NULL,
  created_at TEXT NOT NULL
);
```

Suggested `change_type` values:

- `stream_started`
- `stream_ended`
- `category_changed`
- `entered_desired_category`
- `left_desired_category`

For MVP, store records only when there is a meaningful transition:

- stream starts
- stream ends
- category changes while live
- channel enters a category watched by at least one user
- channel leaves a category watched by at least one user

### `channel_category_preferences`

Stores per-channel category preferences.

```sql
CREATE TABLE channel_category_preferences (
  id TEXT PRIMARY KEY,
  user_id TEXT NOT NULL REFERENCES users(id),
  broadcaster_user_id TEXT NOT NULL,
  category_id TEXT NOT NULL,
  category_name TEXT NOT NULL,
  created_at TEXT NOT NULL,
  disabled_at TEXT,
  UNIQUE (user_id, broadcaster_user_id, category_id)
);
```

### `global_category_preferences`

Stores user-wide category preferences.

If a followed channel starts streaming or switches into this category, the user can be notified.

```sql
CREATE TABLE global_category_preferences (
  id TEXT PRIMARY KEY,
  user_id TEXT NOT NULL REFERENCES users(id),
  category_id TEXT NOT NULL,
  category_name TEXT NOT NULL,
  created_at TEXT NOT NULL,
  disabled_at TEXT,
  UNIQUE (user_id, category_id)
);
```

### `notification_deliveries`

Stores notification attempts and prevents duplicate sends.

```sql
CREATE TABLE notification_deliveries (
  id TEXT PRIMARY KEY,
  user_id TEXT NOT NULL REFERENCES users(id),
  push_subscription_id TEXT REFERENCES push_subscriptions(id),
  broadcaster_user_id TEXT NOT NULL,
  category_id TEXT NOT NULL,
  trigger_type TEXT NOT NULL,
  eventsub_message_id TEXT,
  stream_id TEXT,
  status TEXT NOT NULL,
  error_message TEXT,
  created_at TEXT NOT NULL,
  sent_at TEXT,
  UNIQUE (user_id, broadcaster_user_id, category_id, trigger_type, stream_id)
);
```

Suggested `trigger_type` values:

- `stream_started_in_category`
- `switched_into_category`

The unique constraint prevents repeated notifications for the same user/channel/category/stream/trigger combination.

## User OAuth And Sync Flow

### 1. User Starts Twitch Login

The PWA calls:

```txt
GET /api/auth/twitch/start
```

The Worker redirects the user to Twitch OAuth with:

```txt
scope=user:read:follows
```

### 2. OAuth Callback

Twitch redirects to:

```txt
GET /api/auth/twitch/callback?code=...&state=...
```

The Worker:

1. Validates `state`.
2. Exchanges the code for tokens.
3. Fetches the Twitch user profile.
4. Creates or updates `users`.
5. Stores encrypted tokens in `twitch_tokens`.
6. Starts the followed-channel sync.

### 3. Followed Channel Sync

The Worker or queue job:

1. Calls `GET /helix/channels/followed`.
2. Upserts rows into `followed_channels`.
3. Optionally removes rows no longer followed.
4. Calls `GET /helix/streams/followed` to get the live subset.
5. Updates `channel_state` for live followed channels.

This gives the UI enough data to render:

```txt
live followed channels ordered by viewer_count desc
offline followed channels below
```

## Preference Selection Flow

### Per-Channel Category Preference

When a user selects a category for a specific followed channel:

1. Upsert `channel_category_preferences`.
2. Ensure the broadcaster exists in `monitored_channels`.
3. Ensure EventSub subscriptions exist for the broadcaster:
   - `stream.online`
   - `stream.offline`
   - `channel.update`
4. Seed `channel_state` for that broadcaster.

State seeding should fetch current data from Twitch before relying on comparisons.

Recommended seeding:

- `GET /helix/streams?user_id={broadcaster_user_id}`
- optionally `GET /helix/channels?broadcaster_id={broadcaster_user_id}`

If the channel is already live in the selected category, the product must decide whether to notify immediately. Recommended MVP behavior:

```txt
Do not send an immediate notification on preference creation.
Only notify on future stream starts or future category transitions.
```

This avoids surprising users with notifications for already-known current state.

### Global Category Preference

When a user selects a global category:

1. Upsert `global_category_preferences`.
2. Ensure all currently followed channels are in `monitored_channels`.
3. Ensure EventSub subscriptions exist for each followed broadcaster.
4. Seed `channel_state` for followed broadcasters where missing or stale.

Global preferences increase the number of monitored broadcasters because any followed channel can become relevant.

## EventSub Subscription Strategy

Create EventSub subscriptions globally per broadcaster, not per user.

Bad:

```txt
User A follows Alanzoka -> create stream.online subscription
User B follows Alanzoka -> create another stream.online subscription
```

Good:

```txt
Alanzoka has one stream.online subscription
User preferences map many users to Alanzoka
```

For every broadcaster in `monitored_channels`, ensure:

```txt
stream.online
stream.offline
channel.update
```

Store Twitch subscription IDs in `eventsub_subscriptions`.

Run a periodic reconciliation job:

1. List active EventSub subscriptions from Twitch.
2. Compare with `eventsub_subscriptions`.
3. Recreate missing/revoked subscriptions.
4. Disable unused subscriptions when no active preference requires the broadcaster.

## Event Processing Flow

### 1. Twitch Calls Webhook

Twitch sends a webhook request to:

```txt
POST /api/webhooks/twitch/eventsub
```

The Worker:

1. Reads the raw request body.
2. Verifies the Twitch signature.
3. Handles `webhook_callback_verification` challenges.
4. Checks if the EventSub message ID was already processed.
5. Enqueues the event in Cloudflare Queues.
6. Responds quickly with `2XX`.

### 2. Queue Consumer Processes Event

The queue consumer:

1. Parses event type.
2. Loads previous state from `channel_state`.
3. Builds next state from EventSub payload plus Twitch API fetches if needed.
4. Writes relevant transitions to `channel_state_changes`.
5. Updates `channel_state`.
6. Matches user preferences.
7. Creates `notification_deliveries`.
8. Sends Web Push to active push subscriptions.
9. Updates delivery statuses.

### `stream.online`

On `stream.online`:

1. Fetch current stream data from Twitch using broadcaster ID.
2. Determine current category.
3. Compare with previous `channel_state`.
4. Update `channel_state` to live.
5. Insert `channel_state_changes` with `stream_started`.
6. If category matches user preference, create delivery with:

```txt
trigger_type=stream_started_in_category
```

### `channel.update`

On `channel.update`:

1. Read current `channel_state`.
2. Extract current category from the EventSub payload.
3. Compare previous category to next category.
4. If the channel is live and category changed, update `channel_state`.
5. Insert `channel_state_changes` with `category_changed`.
6. If previous category did not match and next category matches a preference, notify with:

```txt
trigger_type=switched_into_category
```

If the channel is offline, update category/title cache if useful, but do not notify.

### `stream.offline`

On `stream.offline`:

1. Read current `channel_state`.
2. Update `is_live` to false.
3. Clear `stream_id`, `viewer_count`, and `started_at`.
4. Insert `channel_state_changes` with `stream_ended`.

No category notification should be sent for offline events.

## Matching Rules

For a given broadcaster and category:

### Per-Channel Match

Notify user if:

```txt
user follows broadcaster
AND user has active channel_category_preferences row for broadcaster + category
AND delivery was not already sent for same stream/category/trigger
```

### Global Match

Notify user if:

```txt
user follows broadcaster
AND user has active global_category_preferences row for category
AND delivery was not already sent for same stream/category/trigger
```

### Combined Match

If both per-channel and global preferences match, send only one notification.

Use `notification_deliveries` uniqueness to enforce this.

## PWA Notification Flow

This reuses the POC notification handling.

### Subscribe Device

1. PWA registers service worker.
2. User grants notification permission.
3. PWA creates Push API subscription with VAPID public key.
4. PWA sends subscription to:

```txt
POST /api/push-subscriptions
```

5. Worker stores it in `push_subscriptions`.

### Send Notification

When a Twitch event matches preferences:

1. Worker/queue consumer finds active push subscriptions for the user.
2. Worker sends Web Push payload to each subscription endpoint.
3. Browser push service delivers message to the device.
4. Service worker receives `push`.
5. Service worker calls `showNotification`.

Payload example:

```json
{
  "title": "Alanzoka is streaming Software and Game Development",
  "body": "Alanzoka just started streaming a category you follow.",
  "url": "/channels/alanzoka"
}
```

## Background Jobs

### Follow Sync Job

Runs:

- after OAuth connection
- on user request
- periodically for active users

Responsibilities:

- Refresh Twitch token if needed.
- Sync followed channels.
- Update live followed subset.
- Ensure EventSub subscriptions for channels needed by preferences.

### EventSub Reconciliation Job

Runs periodically.

Responsibilities:

- Reconcile local `eventsub_subscriptions` with Twitch.
- Recreate missing subscriptions.
- Mark revoked/failed subscriptions.
- Remove subscriptions for broadcasters no longer needed.

### Token Refresh Job

Runs on-demand before Twitch API calls and periodically for active users.

Responsibilities:

- Refresh expired user access tokens.
- Mark users requiring reconnect if refresh fails.

## Deduplication And Idempotency

Twitch webhooks can be retried. The app must be idempotent.

Use:

- EventSub message ID uniqueness in `channel_state_changes`.
- `notification_deliveries` unique constraint.
- Queue retry handling.

Processing the same Twitch message twice should not send duplicate notifications.

## Initial State And Previous-State Comparison

The assumption is correct: the app needs its own previous state to know whether a category changed into or out of a desired category.

The required approach is:

1. When a channel becomes monitored, seed `channel_state`.
2. On every relevant EventSub event, load previous `channel_state`.
3. Build next state.
4. Compare previous and next state.
5. Store relevant transition in `channel_state_changes`.
6. Update `channel_state`.

Do not rely on the `channel_state_changes` table alone for current comparison. It is history. `channel_state` is the current snapshot.

## Notification Decision Matrix

| Previous State               | Event            | Next State                       | Notify?                                                     |
| ---------------------------- | ---------------- | -------------------------------- | ----------------------------------------------------------- |
| offline                      | `stream.online`  | live in desired category         | yes                                                         |
| offline                      | `stream.online`  | live in non-desired category     | no                                                          |
| live in non-desired category | `channel.update` | live in desired category         | yes                                                         |
| live in desired category     | `channel.update` | live in another desired category | yes, if user follows both categories and delivery is unique |
| live in desired category     | `channel.update` | live in non-desired category     | no                                                          |
| live                         | `stream.offline` | offline                          | no                                                          |
| offline                      | `channel.update` | offline with desired category    | no                                                          |

## Open Product Decisions

### Notify Immediately On Preference Creation?

Recommended MVP behavior:

```txt
No.
```

When a user adds a preference, seed current state but do not notify for already-live matching streams. Only future starts/transitions notify.

### Monitor All Followed Channels Or Only Preference-Relevant Channels?

Recommended MVP behavior:

- If user has only per-channel preferences, monitor only those selected channels.
- If user has any global category preference, monitor all followed channels.

This minimizes EventSub subscriptions while preserving global-category behavior.

### Notification Cooldown

Recommended MVP behavior:

- One notification per user, broadcaster, category, stream, trigger type.
- Do not send repeated notifications for the same category within the same stream unless the stream leaves and re-enters the category and the product explicitly wants that.

The initial `notification_deliveries` unique key can enforce the stricter behavior.

## Deployment Recommendation

Use:

```txt
Cloudflare Pages + Workers + D1 + Queues + KV
```

Reasons:

- Serverless-compatible with Twitch webhooks.
- No always-running backend required.
- D1 gives relational tables for preferences/state/deliveries.
- Queues allow webhook handlers to respond quickly.
- KV is useful for short-lived app-token caching.
- Pages is suitable for the static PWA.

Alternative:

```txt
Vercel + Upstash Redis/Postgres + Upstash QStash
```

This can also work, but Cloudflare has a more unified low-cost stack for webhook receiver + queue + storage.

## MVP Implementation Phases

### Phase 1: Auth And PWA Shell

- Twitch OAuth.
- User session.
- Push subscription registration.
- Basic followed-channel sync.
- Followed-channel list UI ordered live/viewers first.

### Phase 2: Preferences

- Search/select categories.
- Per-channel preferences.
- Global category preferences.
- Preference management UI.

### Phase 3: EventSub

- Create EventSub webhook subscriptions.
- Verify webhook signatures.
- Handle callback verification challenge.
- Queue incoming events.
- Reconcile EventSub subscription state.

### Phase 4: State And Matching

- Seed channel current state.
- Process `stream.online`.
- Process `channel.update`.
- Process `stream.offline`.
- Compare previous/next state.
- Store relevant state changes.

### Phase 5: Notification Delivery

- Match per-channel and global preferences.
- Create `notification_deliveries`.
- Send Web Push.
- Handle invalid push subscriptions.
- Add deduplication and retries.

## Key Risks

- EventSub subscription count grows with unique monitored broadcasters.
- Global category preferences may require monitoring every followed channel for a user.
- Users can follow many channels, so sync and subscription creation must be paginated and rate-limit aware.
- Twitch tokens must be refreshed and protected.
- Push subscriptions can expire or be revoked.
- iOS PWA notifications require the installed Home Screen app path.
- Webhook processing must be idempotent because retries can happen.

## Summary

The MVP does need backend capability, but it does not need an always-running server.

The correct serverless architecture is:

```txt
Twitch EventSub Webhooks
  -> Cloudflare Worker webhook receiver
  -> Cloudflare Queue
  -> D1 state/preferences lookup
  -> Web Push notification sender
  -> PWA service worker displays notification
```

The current-state table is mandatory for category-change comparisons. A channel-update/history table is useful, but it should store relevant transitions after comparing against `channel_state`, not act as the only source of truth.
